# 01 · UI & visual design ideas

Layout, labels, colour and message placement ideas from the shift walkthrough (`00-walkthrough.md`); every idea stays vanilla HTML/CSS/JS and works offline.

## UI-01 · Show messages next to the button that caused them

- **Problem**: Step 1, Loan register issue form. Picking CA-03 for RQ-214 was blocked, but "This equipment type is outside the approved request…" showed up only in the bottom status bar, far below the Save button (pain point 5). A beginner sees nothing happen and clicks Save again. Success messages ("Issued PR-04 to Kabir Sen on slip L-402.") also land in a 12px grey bar.
- **Proposed change**: Add one inline message box (`<p class="msg" role="alert">`) directly above the "Save issue slip" button. Errors use a red-tinted box with a "!" icon and say which field is wrong ("Unit leaving the desk: a camera is not on RQ-214. This request needs: projector, speaker, adapter."). Also give the wrong `<select>` a red border with `aria-invalid="true"` and move focus to it. Successes show as a green toast at the top of the page section ("✓ Slip L-402 saved: PR-04 → Kabir Sen"). The toast stays until the next action and is mirrored into the status bar for screen readers.
- **User benefit**: Errors appear where the student is looking, so they can fix the field right away instead of thinking the app is broken.
- **Effort**: S
- **Files touched**: `app.js` (submit handler for `[data-issue]`, add `s.formError` / `s.flash` to state, render it in `register()`, clear it in `paint()` / on tab change), `styles.css` (`.msg.error`, `.msg.ok`, `[aria-invalid]`).
- **Risks / trade-offs**: If the new state keys are saved, `restore()` has to accept them (the spread already lets them through). Keep the status bar too, so the message is not lost if the student scrolls.

## UI-02 · Colour-coded status badges with icon + word, including "Overdue"

- **Problem**: Step 3, the register shows L-404 AD-12 "Due Fri 8 pm" (13 h late) looking exactly like L-401 "Due Sat 10 am" (pain point 8). `badge()` only has two looks: grey and green. "On loan", "In repair" and "Returned" are all the same grey.
- **Proposed change**: Extend `badge(t, kind)` to a small fixed set, each with a colour, an icon character and a word, so it never relies on colour alone:
  - On shelf: green, ✓
  - On loan: blue, ↗
  - Due soon (due at the next time step): amber, ⏱
  - Overdue: red fill with white text, ⚠ "Overdue · 13 h"
  - In repair: purple/grey striped, 🔧-style wrench drawn with an SVG `<symbol>` (no emoji, to keep the sprite consistent)
  - Returned: muted outline, ✓ "Returned"
  Work out overdue by giving each time step a sortable value (e.g. `shifts[i].at = "Fri 15:45"`) and comparing it with the slip's `due`.
- **User benefit**: The student can spot the one late item at a glance in a crowded morning queue.
- **Effort**: M (needs a small time-ordering helper)
- **Files touched**: `app.js` (`badge()`, new `dueState(loan)`, `register()`, `inventory()`, `shifts` data gets an ordering field), `styles.css` (`.tag.loan`, `.tag.soon`, `.tag.late`, `.tag.repair`, `.tag.done`, with `light-dark()` values for both themes).
- **Risks / trade-offs**: Too many colours can look noisy, so keep it to these 6 and document them in a legend (see UI-11). Red must pass contrast in dark mode.

## UI-03 · Overdue rows float to the top and get a red left edge

- **Problem**: Step 3, the incoming staff member has to read every row to find what is late (pain points 8, 15). The register lists rows newest-first (`.reverse()`), so the oldest and most urgent slip sinks to the bottom.
- **Proposed change**: In "Outstanding" view, sort rows Overdue → Due soon → the rest. Overdue rows get a 4px red left border, a pale red background and the UI-02 badge. Above the list, add a one-line summary chip row: "1 overdue · 1 due today · 0 on time".
- **User benefit**: The first thing on screen is the thing that needs action, matching the real counter question "what's still out?".
- **Effort**: S (after UI-02)
- **Files touched**: `app.js` (`register()` sort + summary line), `styles.css` (`.row.late`, `.summary`).
- **Risks / trade-offs**: A changing sort order can surprise users. Keep the order stable within a group and do not re-sort while a confirm (UI-05) is open.

## UI-04 · Richer slip cards: model, bin and holder at a glance

- **Problem**: Step 3, the slip shows only "L-404 · AD-12". Model and bin live only on the Inventory tab, and AD-15 (Anker) is a look-alike in the same bin C4 (pain point 9). Rows in the register, inventory and requests all use the same two-line `row()`, so slips don't look different from other things.
- **Proposed change**: Give register rows a card layout with three clear parts:
  - Left: a big monospace asset tag "AD-12" styled like a physical sticker (bordered, bold), with the type under it.
  - Middle: "Belkin AVC002 · Bin C4", then "For RQ-214 Film Society · With Kabir Sen".
  - Right: the status badge (UI-02) and the action button.
  When two open or shelf units share a bin and type, show a small amber note under the model: "Look-alike: AD-15 Anker is also in C4. Check the label."
- **User benefit**: The student can match the label on the item in hand to the screen without switching tabs, which cuts down wrong-unit returns.
- **Effort**: M
- **Files touched**: `app.js` (new `slipRow(l)` instead of `row()` inside `register()`, look-alike helper using `assets`), `styles.css` (`.slip`, `.assettag`, `.lookalike`).
- **Risks / trade-offs**: Taller rows mean less fits on screen. On mobile, stack the three parts (see UI-10).

## UI-05 · Make "Record return" a two-step, in-row confirm with Undo

- **Problem**: Step 2, L-402 closed on one click with no confirmation and no undo, and the rows below moved up, so a fast second click can hit the wrong row (pain points 6, 7). Every row has an identical "Record return" button.
- **Proposed change**: Clicking "Record return" expands that row in place (it does not re-render or move the list) into a confirm panel: "Check the label on the item: **AD-12 · Belkin AVC002**", a "Brought back by" dropdown, and two buttons, "Yes, AD-12 is back" (primary) and "Not now". After confirming, the row stays where it was for this view, greyed out with "Returned just now · Undo" and a 10-second Undo link, and only disappears on the next tab switch or refresh. Put the button text in the row too: "Record return of AD-12", so each button says what it does.
- **User benefit**: No accidental closes, an easy fix when a mistake happens, and the list doesn't jump under the cursor.
- **Effort**: M
- **Files touched**: `app.js` (click handler `return` → sets `s.confirming = num`; new `confirm-return` / `undo-return` actions; `register()` renders the expanded state; loans gain `backAt`/`backBy`), `styles.css` (`.row.confirming`, `.row.justdone`).
- **Risks / trade-offs**: Adds one click per return. Overlaps with the workflow agent (who returned it). `restore()` must allow the new loan fields.

## UI-06 · A "Start here" card for each time step on top of the shift bar

- **Problem**: The shift bar is one story paragraph plus a forward button (pain point 15). In step 3 the new staff member must combine the Desk book and Register by hand. The yellow bar's "Move to return time" button looks like any other button, so beginners might jump time by accident (pain point 16, time only moves forward).
- **Proposed change**: Split the shift bar into two parts:
  - Left: the story (unchanged text), with the title in larger type.
  - Right: a short "Your tasks now" checklist built from live state, e.g. step 1 "☐ Issue projector ☐ Issue speaker ☐ Issue adapter (RQ-214)", step 3 "☐ 1 item still out from RQ-214 (AD-12, overdue) → Open in register". Each item is a link-button that jumps to the right tab, and it ticks itself when done.
  Move the time button to the far right, style it as a clear "⏭ Move to return time" pill with a small "Can't go back" caption under it.
- **User benefit**: A beginner always knows what the next action is and where to do it, and doesn't skip time by mistake.
- **Effort**: M
- **Files touched**: `index.html` (shift `<aside>` gets a `[data-tasks]` list and a caption), `app.js` (`paint()` builds tasks from `s.loans` + `requests`), `styles.css` (`.shift` grid, `.tasks`, `.advance`).
- **Risks / trade-offs**: The checklist must not give away the "answer" to the exam's judgment parts. Keep it to factual state (what's open/late), not hints such as "check who is authorised". The story text and 3-step control stay as they are.

## UI-07 · Request progress bar on the Requests tab

- **Problem**: Step 3, the Requests tab still says "RQ-214 · Approved" after everything was issued and returned (pain point 13). The list rows only show event, ID, club and "View form".
- **Proposed change**: Each request row gets a status badge (Not started / Partly out / All out / Partly back / Complete) and a 3-segment mini bar, one segment per approved item: empty = not issued, blue = out, green = back, red = overdue. In the detail view, list items as a checklist: "HDMI projector — PR-04, out on L-402" / "USB-C → HDMI adapter — not issued yet" with an "Issue this" button.
- **User benefit**: The student can see at a glance what a club still has and what's missing before the event.
- **Effort**: M
- **Files touched**: `app.js` (`requestPage()`, new `progress(req)` helper reading `s.loans`), `styles.css` (`.progress`, `.seg.out/.back/.late`).
- **Risks / trade-offs**: The "Issue this" button overlaps the workflow agent's batch-issue idea, so agree on one entry point.

## UI-08 · Issue form that shows the request it's for

- **Problem**: Step 1, the form is four blank dropdowns in a 2×2 grid with no context (pain points 1–3). "Unit leaving the desk" lists every available unit, and "Return by" isn't prefilled, so the student has to remember the request details from another tab.
- **Proposed change**: Lay the form out top-to-bottom as numbered steps (1 Request → 2 Item → 3 Person → 4 Return time). Once a request is picked, show a summary panel to the right (stacked below on mobile): event, "Return by Fri 8 pm", the approved item list with ticks for those already issued, and the request note in a memo-yellow box. Group the unit dropdown with `<optgroup>`: "On this request" first, then "Not on this request" (disabled). Visually mark the prefilled return time with "(from request)".
- **User benefit**: Everything needed to fill in the form is on one screen, so there are fewer wrong choices and no tab switching.
- **Effort**: M
- **Files touched**: `app.js` (`register()` form markup; add a `change` handler for `select[name=req]` that re-renders or updates the panel), `styles.css` (`.form.steps`, `.reqsummary`).
- **Risks / trade-offs**: Prefill and filtering are workflow decisions, so coordinate with the workflow agent. The visual part (numbered steps + summary panel) works by itself.

## UI-09 · Tell row types apart: info rows vs. action rows

- **Problem**: All screens reuse `row()`: Requests ("View form"), Inventory (badge) and Register ("Record return") look the same, and status badges and buttons sit in the same right-hand slot (pain point 7). In step 2 the register had 4 identical-looking rows with identical buttons.
- **Proposed change**: Set a clear visual grammar:
  - Badges = flat, rounded pills, no border, never clickable.
  - Buttons = bordered, with a verb and an icon ("→ View form", "↩ Record return of AD-12").
  - Action rows get zebra striping or more padding (12px) and a hover highlight across the whole row, so the student can see which row the button belongs to.
  - Every row starts with a bold ID column with a fixed width (`grid-template-columns: 7ch 1fr auto`), so IDs line up vertically and are easy to scan.
- **User benefit**: The student can tell what is clickable and which item a button belongs to, so there are fewer wrong-row clicks.
- **Effort**: S
- **Files touched**: `app.js` (`row()` gains an `id` argument; `btn()` labels), `styles.css` (`.row`, `.row:hover`, `.tag` vs `button`).
- **Risks / trade-offs**: A small global change, so check all four screens and both themes.

## UI-10 · Mobile layout fit for a phone at the counter

- **Problem**: Under 650px, the nav becomes a wrapping row of 4 small buttons (5px 7px padding) at the top, and the status bar (where errors appear, pain point 5) is at the very bottom, off screen. Long tab names like "Loan register" wrap unevenly. Rows keep the button on the right, which squeezes the text at 375px.
- **Proposed change**: Under 650px:
  - Turn the nav into a fixed bottom tab bar (4 equal icons + short labels: Requests / Items / Loans / Notes) with ≥48px targets and a count bubble on Loans ("2", red when something is overdue).
  - Make the shift bar collapsible (title + "Show story" toggle) so the list is visible without scrolling, while keeping the time button visible.
  - Stack row contents: text on top, a full-width action button below.
  - Show messages as the top toast from UI-01, never only in the footer.
- **User benefit**: Usable one-handed on a phone or a small tablet on the desk, with the important controls within reach.
- **Effort**: M
- **Files touched**: `styles.css` (`@container (max-width:650px)` and `420px` blocks), `app.js` (`paint()` nav adds short labels/counts), `index.html` (no structural change needed beyond optional `data-short` labels).
- **Risks / trade-offs**: A fixed bottom bar can cover content, so add bottom padding to `.page`. "Restart sample shift" must stay reachable (keep it in the status bar above the tab bar).

## UI-11 · Helpful empty states and a small legend

- **Problem**: The empty register says only "No outstanding slips." (pain point 15). An inventory filter with no matches shows nothing at all, and the Desk book with no notes shows nothing either. Badge meanings are never explained.
- **Proposed change**: Use a shared `empty(icon, title, hint, action)` block: a grey icon, a one-line title and a next step, e.g.
  - Register/Outstanding: "Nothing is out right now ✓ — Everything is back on the shelf. [New issue slip]"
  - Inventory filter "On loan" with no matches: "No items are on loan. [Show all items]"
  - Desk book: "No handover notes yet. Write one before your shift ends."
  Add a collapsible "What do the colours mean?" legend under the register and inventory headers that lists the 6 badges from UI-02.
- **User benefit**: The student is never left with a blank screen wondering whether it's broken, and learns the colour code once.
- **Effort**: S
- **Files touched**: `app.js` (new `empty()` helper; `register()`, `inventory()`, `deskbook()`), `styles.css` (`.empty`, `.legend`).
- **Risks / trade-offs**: Very little risk. Keep the wording consistent with the language agent's plain-words glossary.

## UI-12 · Desk book entries that look like what they are

- **Problem**: Step 2/3, handover notes look the same as club messages (same `.record` card), show the author as "Counter handover", and aren't linked to a slip (pain point 12). In step 3 the key note (Leela has AD-12) is mixed in with older messages.
- **Proposed change**: Use three visual types: club messages (white card, club name in colour, a "From club" label), staff handover notes (memo-yellow sticky-note style with a "Handover" label and a pin icon), and system events (a thin grey line, e.g. "L-402 returned · 7:30 pm"). Above the note box, add optional "About:" chips for open slips (e.g. [L-404 · AD-12]). A chosen chip appears on the note as a link to that slip and as a 📝 marker on the slip row in the register.
- **User benefit**: The morning shift finds the handover note right away and can see it from the slip it relates to.
- **Effort**: M
- **Files touched**: `app.js` (`deskbook()`, notes gain an optional `slip`, `register()` shows the marker), `styles.css` (`.record.club`, `.record.note`, `.record.event`, `.chip`).
- **Risks / trade-offs**: Linking notes overlaps the workflow agent. The visual split by entry type works by itself. `restore()` needs to accept `slip` on notes.

## UI-13 · A stronger desk clock and a time-step progress strip

- **Problem**: The clock ("Desk time Friday · 3:45 pm") is small and right-aligned in the masthead, and nothing shows that the shift has 3 steps or where you are (pain point 16). Due times only make sense compared with the current time.
- **Proposed change**: Under the masthead, add a 3-dot stepper: "● Fri 3:45 pm Pickup — ○ Fri 7:30 pm Returns — ○ Sat 9:00 am Morning", with the current step filled and finished steps ticked. The stepper is display only, and the existing advance button still moves time. Make the clock bigger (20px, tabular numbers). On register rows, show due times relative to now ("Due in 4 h 15 m" / "13 h overdue") next to the absolute time.
- **User benefit**: The student understands where they are in the shift and how urgent each due time is without doing mental maths.
- **Effort**: S–M
- **Files touched**: `index.html` (stepper container), `app.js` (`paint()` renders stepper; relative-time helper shared with UI-02), `styles.css` (`.stepper`, `.clock strong`).
- **Risks / trade-offs**: It must not look clickable, or users will expect to go back in time. Use no hover state and `aria-current="step"`.

## Top 3 picks

1. **UI-01 · Messages next to the button**: The cheapest fix for the most confusing moment in the walkthrough (blocked save with no visible feedback). It helps every form and every mistake.
2. **UI-02 + UI-03 · Status badges with Overdue, overdue rows on top**: Step 3 depends on spotting that AD-12 is 13 h late, and right now nothing on screen shows it. Coloured badges with icons and words, plus urgent-first sorting, turn the morning question into a glance.
3. **UI-05 · In-row return confirm with label check and Undo**: It covers three pain points at once (6 one-click close, 7 jumping list, 9 look-alike units). The fix is visual and local, and it makes mistakes both less likely and easy to undo.
